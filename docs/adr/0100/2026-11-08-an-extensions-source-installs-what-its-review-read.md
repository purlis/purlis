# An extension's source installs what its review read, pinned to its revision

**Amends [ADR 0100](../0100-a-skill-is-installed-from-a-git-source-as-a-pinned-copy-and-never-updates-by-itself.md), 2026-11-08**, tickets #3089 and #3092, and the review of #3088. §8 said the revision takes the commit's place in the lockfile, and that the review, the copy, the pin and the update are the same for every source. This records how that was built.

**The lockfile names an extension's source by its id, pinned to its revision.** An entry is `"source": {"extension": "<id>"}` with `"revision"` in place of `{"url", "branch"}` with `"commit"`, never a mix, and a file holding one is `"version": 2`. A file of git entries alone stays version 1, so an older purlis still reads it. An older purlis refuses a version 2 file whole, which is what `version` is for, rather than misread it (`docs/plane-format.md`).

**The extension is asked once, and what it answered is what is installed.** The review of #3088 asked for three things, and each holds:

1. *The copy takes exactly the bytes the person reviewed, by digest.* A review answers what it read beside what the person reads, held in memory and written nowhere (`source::extension::Held`). The install or update is handed that back. It reads the same review again from it, through the same `reviewed` the git source uses, and refuses where any skill or digest differs from the one accepted, or where the revision does not match.
2. *The extension is not asked again for the files after the review.* The git source fetches its commit again and checks the digests, because git can give back the same commit. An extension's source makes no such promise for a revision, and asking it again would let it answer something new between the review and the copy. Where the install needs a skill the review never read (one it refers to that was met at the level then and is not now), it asks for another review instead.
3. *Paths that collide case-insensitively inside one skill are refused.* An answer naming two paths, or two of their folders, that differ only by case, or one path as both a file and a folder, is refused before the review (`extension::studio::files_of`). macOS and Windows would write those as one, so what was reviewed would not be what landed.

**From the copy on, the git source's code runs.** The copy, the pin, the grant, the widenings, the clash and its offered new name (`<id>-<name>`), and the single commit with the lockfile are `install` and `update`'s own, behind the `SkillSource` trait (`install_from`, `plan_from`). An extension adds no step of its own and cannot change what an install may do.

**An extension's source is asked for updates where the studio asks it anything**: where this machine approved the extension and the project has it on, through the executor's gate (ADR 0101). That approval is this machine's consent. A git source named only by the committed lockfile still waits for Confirm, because its URL is the team's, not this machine's choice. The check asks for its listing alone. An update's diff is from the copy here, since the extension is not asked for the pinned revision.

**Not built here.** An extension's skill is updated on its own. Several updates accepted at once (#5354) refuse it, since each needs the bytes its own review read. `purlis skill update` lists and updates such a skill, but `purlis skill install` takes a git source only. An install from an extension's source is the studio's for now.
