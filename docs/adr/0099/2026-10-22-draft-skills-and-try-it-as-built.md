# Draft skills, Try it and the throwaway piece, as #2772 built them

**Amends [ADR 0099](../0099-a-skill-lives-at-a-level-a-project-skill-reaches-a-workspace-by-grant-and-the-narrowest-copy-wins.md), 2026-10-22**, ticket #2772 (SK-9), spec #2762 decisions 13, 38, 50 and 52. The amendment of 2026-10-21 on changing a skill said a chat's change becomes a draft the person accepts in the studio. This records how.

## A chat never writes a skill's files

- **A plane skill's file is any file below a level's skills**: `skills/<folder>/…` or `skills.local/<folder>/…` at the project's root or in a workspace (`drafts::draftable`). Never a dot-name, a `package.json` or a `hooks` folder below the skill's folder, which the proposed-change rule (PC-1) keeps from `.claude/skills` too; never a workspace that is not there; never a path with a link in it.
- **In Claude Code**, sandboxed or not, the chat's `Write`, `Edit` or `MultiEdit` of one is read by its `pretooluse-edit` hook and handed to the app on the proposed change's road (`Ask::Propose`, #1975). The tool is refused with words that say the draft is in the Skill studio. **In another harness** the chat runs `purlis propose <file> --from <draft>`, which now takes a skill's file too.
- **The app keeps it as a draft** instead of holding it as a proposed change, where the `skill-studio` flag is on. Where the flag is off, or the app is older, the edit is what it was before.
- **A sandboxed chat is denied writing the skills folders themselves**, while the flag is on (`sandbox::skills_held`): `skills/` and `skills.local/` at the root, in each workspace and in each persona's folder. A skill runs its `!` commands when it is used and reaches every chat its level reaches, the reason `.claude/skills` is held (ADR 0067 §5). So a chat in any harness cannot plant a skill around the draft.
- **Skill folders at every level are held, including levels created later.** The project's own levels are held by their paths; every workspace's and persona's, there now or made later, by one pattern a level (so the rules handed to a harness in one argument stay the same size however many workspaces there are) (`workspaces/*/skills`, `personas/*/skills.local` and the like), which Claude Code reads as a glob and purlis's own wrap, on macOS and Linux, as a regular expression. And where a backend cannot hold a pattern, a level made while a sandboxed chat runs reaches no chat until that chat closes (`skills::levels`): the host notes the workspace and persona folders there at each sandboxed chat's start, in this machine's state, and a skill from a folder that is not in a chat's note is left out with a reason. When the chat closes, every folder it could have made stays left out, "made by a chat", until the person accepts it in the Skill studio, as a draft waits for its Accept. A folder the person makes, in the window or from their own terminal, is vouched for; one the app makes on a chat's own request is not, and a chat's own command cannot write the notes.
- **No clone is named `skills` or `skills.local`** (`repocmd::clone::destination`): a workspace keeps its skills in a folder of that name, so a pattern never holds a clone's root.
- **An unsandboxed chat is not held.** Its Claude Code edit of a skill's file still becomes a draft, through the hook, but any other write it makes, by a shell command or by a harness without the hook, lands directly, as every unsandboxed write does.
- **A persona's skills folder is held and not drafted.** A persona level is no `Level` of the studio's changes yet, so a write there is refused by the sandbox alone. Drafting a persona's own skill waits for persona skills to be changed in the studio.

## A draft is kept on this machine, one a skill

- Decision 52 says a draft is "a local skill until it is accepted". It is kept on this machine, as a local skill is, but **not** in a level's `skills.local/`: every chat at that level reads a local skill, and a draft must reach no chat but its Try it. It lives in the state directory's `skill-drafts/<id>/` (`docs/plane-format.md`), which no save stages and no chat may write.
- **One draft a skill.** `<id>` is derived from the level and the skill's folder, so a second write to the skill, from any chat, adds to the same draft. An `Edit` is made to the draft's copy of the file where the draft has one, else to the project's.
- **Each file keeps the base it had** when the draft first changed it. Accept refuses a draft whose project file changed since, and the studio says so. It is never merged.
- **The window is told on the asks' event** (`asks-changed`), which a draft's arrival raises without being an ask, so the studio and the chat's tab read the drafts again. The Inbox lists no draft.

## Accept is one commit, Reject deletes

- **Accept** writes each of the draft's files into the skill's folder, only while the project's file is what the draft's base says, and commits exactly those files through the plane's one save (`planegit::save_paths`), as each change of #2770's is. A local skill's draft is written and left uncommitted. A draft whose instructions the live lint finds a problem in, a new skill without instructions, or one whose name a built-in skill or another skill of the level has, is refused.
- **Reject** removes the draft's folder through the handle of the folder that holds it.

## Try it runs in a throwaway piece

- The ticket asked for the smallest throwaway piece Try it needs, which grading (#2779) will use too. **It is a folder, not a worktree**: `workspaces/.throwaway/purlis-try-<id>`, made new and private. A worktree needs a repo, and a draft at the project's root has none. It is inside the project because a sandboxed chat starts only in a folder of the project (the ruling of 2026-10-03); a first build put it in the person's temp folder, and a sandboxed project refused the chat. A dot-name below `workspaces/` is no workspace, git ignores it with every LOCAL workspace's files, and the plane's save excludes it whatever the `.gitignore` says (`planegit::SAVE_STAGES`), so the scratch chat's writes never reach a commit.
- **The skill is laid out in this machine's state, in `skill-tries/<id>/`**, as the one project skill of a project of its own. The layout is the project's files of the skill with the draft's over them. The host arms a chat whose folder is a try's piece from that folder instead of the project (`drafts::tried`), at its root and as no persona. So its set is the built-in skills and the draft alone, on every route: a Claude Code or opencode chat's folder of links, and a Codex chat's briefing and its skill-run reads. Only this machine's state names a piece, and no chat writes the state, so a chat cannot make another folder a try.
- **The harness is the draft's own level's** (decision 50): the profile of the chat that drafted it where it still runs at that level, else of another chat there, else the project's default (no workspace names a default profile of its own today); or the one the person picks in Try it's list. Its turn-offs are read from the chat's own environment, so a profile's own config folder (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) is the one whose skills are turned off. The prompt is typed and never sent, as a curation chat's is.
- **Closing the chat ends the try**: the piece and `skill-tries/<id>/` are removed once its program has had time to end, where no other open chat stands in the piece (a restart starts before the chat it replaces ends). Each time the app writes its record of open chats, and so at every launch, it ends every try no chat on that record stands in, which a quit or a crash left, once it is older than two minutes. Removal is of the names purlis made, through folder handles, never following a link. **What is left is the skill run**, which the plane's event log keeps under the skill's name.
- **Every harness skill and plugin is off** in a scratch chat, by the per-chat switches #2769 measured (`drafts::alone_on`): Claude Code's `enabledPlugins` false and `skillOverrides`, Codex's `-c skills.config`, opencode's `permission.skill` deny. A built-in skill's name is never turned off. So the chat has the built-in skills and the draft alone. A piece is no clone, so no repo skill reaches it.
- **Its writes reach no save.** A sandboxed scratch chat writes its throwaway folder alone, as every sandboxed chat writes only its own folder; the folder is ignored by git and excluded from every save.

## What was rejected

- **Holding a draft as a proposed change.** A proposal is an ask in the Inbox with Apply; a draft is tried first, and the spec says nothing else asks for it.
- **A draft in `skills.local/`.** Every chat at the level would get it before the person tried it.
- **A worktree of the plane as the throwaway piece.** A plane without git, or one mid-save, could not cut one, and the chat would stand in the project's tree.
