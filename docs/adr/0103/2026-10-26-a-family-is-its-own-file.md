# Amendment, 2026-10-26: a family is its own file

Operator ruling, 2026-10-26: **two pull requests that add two families never touch the same
lines.** Until now each one added its family to the end of `MANIFEST`, its module to the end of
the list under it, its tests' module to `theme.rs`, its name to the family lists of three tests,
a row to `docs/themes.md`'s table and an import to `styles.css`, and the generated files beside
them (the theme schema, whose keys followed the manifest's order, and the stories' copy of the
built-in themes, which held each appearance's parts stylesheet on one line) all changed at the
same place, so every family pull request conflicted with every other on each merge.

- **A family is its own file.** `crates/purlis-core/src/theme/parts_<family>.rs` declares it as
  `pub(super) const <NAME>: Family = Family { … }`, its `name` and `since` the first lines inside
  it; its tests are `parts_<family>_tests.rs`. `build.rs` reads the directory and writes the
  module of each, the test module of each and `MANIFEST`, which `parts.rs` and `theme.rs`
  include. The families `parts.rs` held itself (button, field, text input, textarea, tabs,
  editor, tooltip) moved to files of their own.
- **The manifest's order is a rule, not a list.** What versions 1 to 12 shipped comes first, in
  the order they shipped it (`build.rs`, `SHIPPED`, frozen: version 12's digest holds it); every
  later family follows by the version it came in, then by name, `NEXT` last. A release that gives
  `NEXT` its number moves nothing, so the digest of every later version is taken over a stable
  order, and no family's place depends on what another pull request writes.
- **What a pull request regenerates is in name order.** The schema's part keys and
  `docs/themes.md`'s family table (now written from the manifest, one row a family, and held to
  it by a test) list the families by name, so two new families add their lines in two places.
  The stories' copy of the built-in themes keeps each parts stylesheet a rule a line.
  `styles.css` imports the families that need a place of their own by name; the build puts every
  other family's stylesheet at its `@families` line, by name.
- **The tests derive their family lists from `MANIFEST`.**
- **Kept in git, regenerated by one command each, and checked by CI** rather than derived only
  on `main`: `main` takes no push but a pull request's merge (its required checks and linear
  history hold for administrators too), and a bot's follow-up pull request after each merge
  would leave every open pull request behind `main` again. The schema is published at a
  release's tag, and the stories' copy is read by the web and story jobs, which build no Rust.

A pull request can still meet another on a generated file where two families' names sort next to
each other with nothing between them; the fix is the one command that writes the file again.
