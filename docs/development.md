# Developing purlis

How the repository is laid out, how to build and check it, and how a build you can install is
made. [CONTRIBUTING.md](../CONTRIBUTING.md) says how a change gets in.

## Layout

| Path | What |
| --- | --- |
| `crates/purlis-core` | The core: projects, workspaces, personas, memory, vaults, the forges, the harnesses and the sandbox chats run in. No UI, no Tauri |
| `crates/terminal` | A program in its own pseudo-terminal, the headless engine that keeps its screen, and the fork lock every program is started under, with nothing of git, HTTP or the keyring: what a session host owns terminals with. The core re-exports it |
| `crates/purlis-cli` | The `purlis` binary, with `charter` as an alias, called by hooks, scripts and agents |
| `crates/stand-in` | Test-only: the one way a test writes a program it is about to run |
| `crates/same-user` | Whether a socket's peer, a directory or a file is this user's alone: the one copy of the checks `charterd.sock`, the hook sockets and the client scopes' credentials rest on |
| `crates/browser-engine` | The engine a browser runs on: a pinned Chrome for Testing, verified against its manifest before it runs, started over an inherited DevTools pipe with no port, in a process group its keeper ends when the host ends |
| `crates/scale-project` | Developer-only, never shipped: a seeded project at the scale spec's target size (#5486), written through the core's own writers, the index the session host would build on it, and the timing of a git standing look on it. What the nightly scale run measures on |
| `crates/skill-grader` | Developer-only, never shipped: the CI grader (#5727, #5728, spec #5714). Which built-in skills a change grades, Claude Code, Codex or opencode started headless on their trigger tests as a chat in the window is armed, among the crowd fixture (`ci/skill-grades/crowd`) and bare, and the scores in the run's summary; and `skill-grader optimise`, the description optimiser (#5740), which proposes a built-in's description from its failing tests and grades it. `.github/workflows/skill-grades.yml` runs it once per harness with the `skill-grades` environment's keys, which `ci/skill-grades/wizard.sh` sets up |
| `crates/persona-statistics` | purlis's first built-in extension, and the executor's first consumer: the persona statistics view (ADR 0041 stage 2). The release build assembles it into the app's resources (`persona-statistics assemble <dir>`), and it links the core's stats code so its numbers are `purlis persona stats`'s |
| `app/` | The desktop app: React + TypeScript UI |
| `app/src-tauri` | The app's Rust side: Tauri commands that call the core |
| `app/src/bindings.ts` | The commands as TypeScript, generated by `tauri-specta`. Never edited by hand |
| `app/src/theme` | The themes, as data: semantic tokens the CSS and xterm are both generated from ([`docs/design-system.md`](design-system.md)) |
| `tools/relaunch.mjs` | The app quit and started again, which no scenario spec can do |
| `site/` | purlis's website and docs: an Astro Starlight site built from `docs/` and checked on every PR (`.github/workflows/docs.yml`). Not published yet (ruling V38) |

## Build and check

Requires stable Rust (`rust-toolchain.toml` picks it) and Node 24 (`.nvmrc`). On Linux, install
[Tauri's system dependencies](https://v2.tauri.app/start/prerequisites/#linux) first.

```bash
cd app && npm install
npm run tauri dev          # the app, with hot reload
```

Everything CI checks, runnable locally:

```bash
cargo fmt --all --check
cargo clippy --all-targets -- -D warnings    # core and cli
cargo test
cargo deny check                             # licences and advisories (brew install cargo-deny)
tools/no-orphans.sh -- cargo test --workspace   # and that no test left a process running

cd app
npm run typecheck && npm run lint && npm run format:check && npm test
npx tauri build --debug --no-bundle          # the app crate, with its frontend built first
```

`tools/no-orphans.sh` counts every process of yours that started while the suite ran and is still
running after it, so on a machine doing other work it names that work too. CI runs it with
`--reap`, which also kills each one by pid; leave that off on a shared machine.

purlis's website and docs, with the link check and the check that every page in `docs/` is in the
sidebar, which CI runs on every pull request:

```bash
cd site && npm ci
npm test && npm run build    # dist/; `npm run dev` serves it with reload
```

The commands the UI calls are generated into `app/src/bindings.ts`. Running the app writes it,
and a test fails when it is out of date; to write it without running the app:

```bash
cargo test -p purlis-app -- --ignored
```

The scenario tests run against a built app; CI builds it with the `e2e` cargo feature first.
One test cannot live among them — the app ended and started again, because WebdriverIO's
service keeps one app process for a whole run and a spec that quits takes the run with it:

```bash
npm run e2e:relaunch          # in app/, with the app already built with the `e2e` feature
```

CI also runs clippy on the app crate (`--workspace`), after creating an empty `app/dist` so it
compiles without a frontend build.

On Linux, CI also holds the built app's cold start to the spec's 2 s limit on the desktops
purlis#24 is about. Each case launches the debug build once, discarded, then five times on
a fresh HOME and XDG profile each. The median of the five must be inside the limit and no one
of them past 2.5 s: a debug build on a shared runner is noisy (one launch in five went 63 ms over
while the rest sat near 1.35 s), and a release build — the one users run — costs about 6.5 min
of fat LTO on the runner against about 1 min for the debug build CI already makes. The
discarded launch pays for a disk cold since boot or install (the binary and GTK/WebKitGTK's
libraries), which a person pays once; its time is printed as "cold disk, once per boot or
install: reported, not gated". The fresh profile makes each held launch pay what a new user's
first launch pays: Mesa compiling WebKit's shaders into `~/.cache/mesa_shader_cache`. After the
debug build above, with `xvfb`, `xauth`, `dbus-x11` and `i3` installed:

```bash
tools/coldstart-linux.sh bare       # X with no window manager, on the session bus as found
tools/coldstart-linux.sh i3         # i3 under X11, on the session bus as found
tools/coldstart-linux.sh i3-nobus   # i3 under X11 with no session bus, as `startx` into i3
```

`APP` names another binary and `LIMIT_MS` and `CEILING_MS` another limit and ceiling.

CI runs a `windows` job too, every night but not on a pull request or a push to `main`,
and it is **evidence, not a gate**: `continue-on-error`, not one of the eight required checks,
and it reports the whole `cargo check` error list rather than stopping at the first line.
Nothing has been ported to Windows, so it is expected to be red — what it is for is making
"what is true on Windows" a measurement instead of a guess. What it has found so far is
[ADR 0031](adr/0031-windows-gets-charters-guards-or-it-gets-no-charter.md), and #95 to #103.

Every plane write is also checked against what the Python charter answered for the same
command on the same fixture plane: its output, its exit status and the tree it left, byte for
byte. Those answers were recorded once, on 2026-09-23, and are replayed against every build with
no Python anywhere (ADR 0046):

```bash
cargo test -p purlis-cli --test recorded_behaviour                  # every scenario
cargo test -p purlis-cli --test recorded_behaviour -- save- doctor-  # only those
```

A change that is meant to move a recorded answer re-records it
(`CHARTER_RECORDED_BLESS=1`, same command) and says why in the PR.

To measure the app against the spec's limits, with tmux beside it as a reference (macOS; it
takes about twenty minutes, opens windows on screen and brings each to the front, and needs the
screen unlocked — a locked or sleeping display is not drawn, so nothing would paint):

```bash
node tools/bench.mjs          # builds release, then prints and writes target/bench/<time>/results.json
```

To measure purlis on a project at the scale spec's target size (#5486: 1,000 workspaces, 100
personas, 100,000 + 100,000 memories), as `.github/workflows/scale.yml` does each night on macOS
and Linux. The project is about 220,000 files and 1 GB; the same seed and `--at` give the same
bytes:

```bash
cargo build --release -p scale-project -p purlis-cli
target/release/scale-project generate --out /tmp/scale-project   # --small for a few of everything
git -C /tmp/scale-project init -q && git -C /tmp/scale-project add -A && git -C /tmp/scale-project commit -qm seed
node tools/scale-run.mjs --project /tmp/scale-project --os macos --out rows.jsonl   # index build, hook, recall, git standing
node tools/scale-report.mjs rows.jsonl                                              # each against #5486's budgets
```

`scale-run.mjs` builds the project index first (`scale-project index`, as the session host does
when it opens a project) and times the hook and `recall` on it: the CLI never writes an index,
so timed without one they measure the file scan the index replaces. On a project with an index
already, `scale-project index` sweeps it instead of building it, so its row is a full build only
on a fresh project. The window's idle minute waits for the host to log that the index is ready.

To grade built-in skills' triggering as `.github/workflows/skill-grades.yml` does on a pull
request (it calls a model, so it costs money and needs a key of your own; the tests never do).
A built-in's trigger tests are its `evals/triggers.json`, and its tier, neighbours and a
source per test are `evals/sources.json` beside them (`docs/ci-grader.md`):

```bash
cargo build -p purlis-cli -p skill-grader
npm install --global "@anthropic-ai/claude-code@$(target/debug/skill-grader pin claude-code)"
mkdir /tmp/grade-plane && (cd /tmp/grade-plane && "$OLDPWD/target/debug/purlis" init --forge github --owner skill-grades)
ANTHROPIC_API_KEY=… target/debug/skill-grader grade --skills purlis-secrets \
  --program "$(command -v claude)" \
  --purlis "$PWD/target/debug/purlis" --cwd /tmp/grade-plane --records /tmp/grade-runs
```

Codex and opencode the same way, each on its own pin: `--harness codex` with
`npm install --global "@openai/codex@$(target/debug/skill-grader pin codex)"`, `--program
"$(command -v codex)"` and `OPENAI_API_KEY` (handed to Codex as `CODEX_API_KEY`), or `--harness
opencode` with `npm install --global "opencode-ai@$(target/debug/skill-grader pin opencode)"`
and `ANTHROPIC_API_KEY`. Each is armed by `Harness::state_hooks`, as a chat in the window is.

To improve a built-in's description, the description optimiser (#5740) grades the current one,
asks Claude Code for a rewrite from the trigger tests that failed, grades the rewrite on a copy
of the plugin, and prints both descriptions and both scores. It changes no file unless given
`--write`, which puts that run's proposal in the skill's `SKILL.md`; you decide what is
committed. It costs two grades and a proposal, on your own keys, handed in by `purlis secret
exec` so no key is typed or printed (it takes any key out of what it says):

```bash
purlis secret exec <vault> --env ANTHROPIC_API_KEY=<key> -- \
  target/debug/skill-grader optimise purlis-secrets \
  --program "$(command -v claude)" \
  --purlis "$PWD/target/debug/purlis" --cwd /tmp/grade-plane --records /tmp/optimise-runs
```

On Codex or opencode, add `--harness` and `--proposer "$(command -v claude)"`; Codex also needs
`--env OPENAI_API_KEY=<key>`.

### A built-in skill's description: the house style

A harness picks a skill by its description alone, among every other skill the person has, so a
built-in's description is written as a trigger (spec #5714, Q15 and Q30):

1. **The situation first, in people's words.** Open with when it is for ("When this purlis chat
   is ending, …"), not with what the skill is.
2. **The word purlis**, in prose, so a request about purlis finds it and a generic request for
   another tool does not.
3. **The phrases people use.** A `Use when asked to …` sentence with the verbs people type
   ("hand off", "wrap up", "retire", "dispatch"), drawn from the trigger tests that should start it.
4. **A "Not for" clause per neighbour**, short: `Not for <their situation> (purlis-<name>).`
   The neighbours are the skills its sources file declares (`neighbours` in
   `evals/sources.json`), the same list its near-miss tests come from, so the boundary
   is written once and measured.
5. **About 290 characters**, because every built-in's description together is at most 5,000
   (Q37), and 5,100 until the built-ins are trimmed back to it (ADR 0102, amended 2026-11-12):
   Codex's and opencode's default budgets are 8,000 characters, so the built-ins leave about
   3,000 for the plane's own skills (at least 2,800, and 2,750 until then). One
   description is never over 1,024, where Codex cuts it, and is plain YAML: no `: ` or ` #` in
   it. A longer description takes its characters from another built-in's.

The shipped-skill check
(`crates/purlis-cli/tests/it/every_shipped_skill_passes_the_built_in_checks.rs`) fails a
description without the word purlis, over 1,024 characters, or whose "Not for" clauses leave out
a declared neighbour, the built-ins' descriptions together over that cap
(`purlis_core::skills::BUILT_IN_DESCRIPTIONS_MOST`, naming the biggest), and a built-in without trigger tests (`evals/triggers.json`), an
`evals/sources.json` that reads, or a tier, so no built-in ships unmeasured. A neighbour purlis does not ship, such as a
skill of the plane's own, is named in the description's prose and its requests are plain
negatives. The trigger grade measures the rest. A built-in's trigger bar, strict
(≥95% recall, ≤5% false triggers) or standard (≥85%, ≤5%), is the `tier` of the same
sources file; moving a skill between bars is a reviewed change.

The window's half (the sidebar answer, the watcher's setup, a minute of idle CPU, and the chat
events busy chats send the window) is `npm run e2e:scale` in `app/`, on a release `e2e` build:
`app/e2e/wdio.scale.conf.ts` says what it needs. A missed budget fails nothing: the nightly run
keeps one issue labelled `scale-regression` open while any is missed.

## CI's caches

The repository may hold 10 GB of Actions cache. Past that, GitHub evicts the least recently used
entries, so a cache that does not fit pushes out one a gate reads. **Only `main` saves a cache.** A
pull request or a merge queue branch restores what `main` saved and saves nothing.
`the_workflows_run_only_what_they_pinned.rs` (`release-manifest`) fails on any step, in a workflow
or a `.github/actions/` action, that could save on another ref:

- rust-cache needs `save-if: ${{ github.ref == 'refs/heads/main' }}` or `save-if: false`.
- actions/cache needs to be `actions/cache/restore` followed by an `actions/cache/save` under
  `if: github.ref == 'refs/heads/main'`.
- For npm, use `./.github/actions/npm-ci`. setup-node's own cache saves on every ref, so every
  setup-node says `package-manager-cache: false`.
- sccache writes only as `github.ref == 'refs/heads/main' && 'READ_WRITE' || 'READ_ONLY'`.

What `main` keeps, measured on 2026-11-08 (#5858):

| Cache | Size | Who restores it |
| --- | --- | --- |
| rust-cache `rust` (Linux) | 1.45 GB | `rust`, `rust-doctests`, `git-lfs`, `recorded`, `stress` |
| rust-cache `scenario-linux` | 1.05 GB | the Linux scenario legs, Pool setup's run, `stress` |
| rust-cache `app` (Linux, macOS) | 0.90 + 0.67 GB | `app` |
| rust-cache `lint` | 0.73 GB | `lint` |
| rust-cache `scenario` (macOS) | 0.49 GB | the macOS scenario legs, `stress` |
| rust-cache `dev-release` (outcome bars) | 0.76 GB a platform | `outcome-bars`, `outcome-bars-linux` |
| rust-cache `bench` | 0.21 GB | `bench` |
| sccache (macOS) | about 1 GB, new entries every merge | the macOS builds |
| npm (`npm-ci`) | 0.1 GB a lockfile and OS | the web, app, scenario, stories and docs jobs |
| Linux packages | 0.06 GB a package list | every Linux job |
| CodeQL's overlay base | 0.26 GB a merge | CodeQL |

A job that builds what another already caches restores that one by `shared-key` and saves none,
rather than taking a cache of its own. Measure with
`gh cache list -R purlis/purlis --limit 1000 --json key,ref,sizeInBytes,lastAccessedAt`.

## A build you can run

CI builds the app but never bundles it, so nothing in a PR is installable. The `release`
workflow does, three ways: a `v*` tag publishes to the **stable** channel, a green `main`
publishes to the **dev** channel, and **release → Run workflow** on any branch builds a macOS
`.app`/`.dmg` and a Linux `.deb`/AppImage as run artifacts, published nowhere. The job summary
prints what to type to install each one. A build started by hand uses the stable build's
`release` profile unless you pick `dev-release`, the lighter profile the dev channel is built
with ([ADR 0092](adr/0092-the-channels-differ-in-optimisation-profile-and-bundle-set-and-in-nothing-else.md)).

The app updates itself from those channels, and `purlis update --channel dev|stable` picks
one. Published builds are updater-signed (minisign) and Developer ID signed, **not notarized**,
so a first install from a browser meets Gatekeeper once and updates do not. How that works, and
the keys and secrets only the operator can set up, are in [`docs/updating.md`](updating.md)
and [ADR 0042](adr/0042-charter-updates-itself-and-nothing-it-cannot-verify-reaches-it.md).

The bundles carry the `purlis` binary beside the app's own executable, because the app runs
that one for hooks and deliberately does not look at `PATH`. It is staged as a Tauri sidecar by
the workflow and declared in `app/src-tauri/tauri.release.conf.json`, which exists only so that
a plain checkout — where the sidecar has not been built — still builds in CI.
